# KubeLB CCM on `kubev-cluster`

Publishes Services from the KubeVirt demo cluster through the KubeLB manager behind
`kubelb.kkp.demo.kubermatic.io`, so a VM can get a real public IP instead of a
`<pending>` LoadBalancer.

Same shape as the fog reference
(`fog/bcp1/layer2/kubermatic-deployment/80_sub-environments/31_kkp-master-seed/50_services/01_kubelb`),
adjusted for this repo. Differences are listed at the bottom.

## The environment

| | |
|---|---|
| Manager        | KubeLB **EE v1.5.0**, `34.40.127.172:6443` (`kubelb.kkp.demo.kubermatic.io`) |
| Tenant         | `kubev-vm-ccm` -> namespace `tenant-kubev-vm-ccm` on the manager |
| CCM            | **Community Edition v1.5.0**, `quay.io/kubermatic/kubelb-ccm` (public image) |
| Runs on        | `kubev-cluster`, k8s 1.34.7, namespace `kubelb` |
| Node addresses | InternalIP only (`10.32.0.0/24`), no `ExternalIP`, no `providerID` |
| Scope          | opt-in: `spec.loadBalancerClass: kubelb` |
| HTTP           | Ingress on (`ingressClassName: kubelb`); Gateway API off |

CE, not EE, is a deliberate choice: the EE image is private on quay and would need the
`kubermatic-quay.io` regcred that fog keeps in sops. The cost is the EE-only features -
`backendTransport: MTLS`, the `Tunnel` CRD, and WAF. None of them are needed here; see
[Verified](#verified-the-manager-reaches-10320024) and [Known limit](#known-limit-vms-in-a-custom-kube-ovn-vpc-are-not-reachable).

## Files

| File | Purpose |
|---|---|
| `helmfile.yaml.gotmpl`             | The release: OCI chart, namespace, presync hooks |
| `values.yaml`                      | Tenant name, address type, scope, controller toggles |
| `presync.sh`                       | Namespace + chart CRDs + `secret/kubelb-cluster` + token check |
| `res/ingressclass.yaml`            | `IngressClass/kubelb` (cosmetic - see below) |
| `kubelb-kubev-vm-ccm.kubeconfig`   | Tenant credential for the manager. **Gitignored** (`*kubeconfig`) |

## Prerequisites

`helm`, `helmfile` and `kubectl` on `PATH`, plus these in `../demo.env` (gitignored):

```bash
KUBECONFIG_KUBEV=...                 # the KubeVirt demo cluster
KUBELB_CCM_KUBECONFIG=.../kubelb-ccm/kubelb-kubev-vm-ccm.kubeconfig
KUBELB_TENANT=kubev-vm-ccm
KUBELB_VERSION=v1.5.0
KUBELB_CHART=oci://quay.io/kubermatic/helm-charts/kubelb-ccm
```

The tenant kubeconfig is **not** in git - the token is a live credential and this repo is
public. Fog solves this with sops; here `presync.sh` builds the Secret from the file on
disk. To re-fetch it (needs admin on the manager, not this token):

```bash
kubectl -n tenant-kubev-vm-ccm get secret kubelb-ccm-kubeconfig \
  -o go-template='{{ index .data "kubelb" }}' | base64 -d > kubelb-kubev-vm-ccm.kubeconfig
```

## Install

```bash
cd hack/demo-setup
just kubelb-diff      # render only, no cluster writes (helmfile template skips presync hooks)
just kubelb-apply     # presync hooks + helm upgrade --install
just kubelb-status    # CCM pod + which Services opted in
just kubelb-tenant    # manager-side view: TenantState, LoadBalancers, Routes, Addresses
just kubelb-logs      # follow the CCM
```

`presync.sh` runs before every apply and is idempotent:

1. `namespace/kubelb`
2. the chart's `crds/` - helm lays those down on the **first** install only and never on
   upgrade, so a chart bump reaches them no other way
3. `secret/kubelb-cluster`, key `kubelb`, mounted by the CCM at `/home/nonroot/.kube`
4. an `auth whoami` against the manager, so an expired token fails here instead of as a
   CrashLoopBackOff ten minutes later. It also asserts the token's namespace matches
   `KUBELB_TENANT`.

## Publishing a Service

Scope is **opt-in**. The cluster already carries 17 LoadBalancer Services stuck
`<pending>` - 12 of them `kubevirt-ccm` mirrors for KKP user clusters, the rest RDP/SSH on
the demo VMs. The chart default (`useLoadBalancerClass: false`) would hand every one of
them a public IP on the first sync, so `values.yaml` sets it to `true`.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-vm
spec:
  type: LoadBalancer
  loadBalancerClass: kubelb        # <- without this the CCM ignores it
  selector:
    vm.kubevirt.io/name: my-vm
  ports:
    - port: 22
      targetPort: 22
```

> **`spec.loadBalancerClass` is immutable.** An existing Service cannot be opted in:
>
> ```
> $ kubectl patch svc win10-demo -n kubermatic-virtualization \
>     --type=merge -p '{"spec":{"loadBalancerClass":"kubelb"}}'
> The Service "win10-demo" is invalid: spec.loadBalancerClass:
>   Invalid value: "kubelb": may not change once set
> ```
>
> Delete and recreate it. For the `kubevirt-ccm` mirror Services in
> `kubermatic-virtualization` that is not an option at all - they are generated by the
> KubeVirt cloud-controller-manager, which does not set a load balancer class. Those need
> `useLoadBalancerClass: false` (and the blast radius that comes with it).

To widen the scope later, flip `kubelb.useLoadBalancerClass` to `false` in `values.yaml`
and re-apply. Every pending LoadBalancer on the cluster is adopted on the next sync; the
tenant's limit on the manager is 50.

### Ingress

`useIngressClass: true`, so only Ingresses with `ingressClassName: kubelb` are picked up.
`res/ingressclass.yaml` creates that class. It is **cosmetic** - the CCM does a plain
string compare on `spec.ingressClassName` and never reads the IngressClass object. It is
deliberately not annotated `is-default-class`, or every class-less Ingress on the cluster
would start getting a public IP.

Gateway API is off. `envoy-gateway-system` already runs here and owns the Gateway API CRDs
(bundle v1.4.1, experimental channel); pointing the CCM's CRD controller at them would put
two controllers on the same objects. To enable it anyway, set `enableGatewayAPI: true` and
leave `installGatewayAPICRDs: false`.

## Verified: the manager reaches `10.32.0.0/24`

**Resolved 2026-09-03.** `nodeAddressType: InternalIP` is forced - the nodes have no
`ExternalIP` and no `providerID`, so `ExternalIP` would publish an empty address list. The
CCM hands the manager `10.32.0.18:<nodePort>` and friends, and the open question was whether
the manager's envoy could dial them.

It can. `svc/win10-demo` came up on `34.159.77.166` and answers RDP end to end:

```
$ python3 -c '...X.224 Connection Request...'
19 bytes: 03 00 00 13 0e d0 00 00 12 34 00 02 1f 08 00 02 00 00 00
          ^^ TPKT            ^^ Connection Confirm      ^^ RDP_NEG_RSP
```

That is the Windows VM itself answering, not an edge proxy - the failure mode documented in
`../README.md` (TCP accepted, RST with zero bytes) does not occur here, so CE stays
sufficient.

## Known limit: VMs in a custom kube-ovn VPC are not reachable

KubeLB delivers a public IP and reaches the node, but the last hop is a plain
`nodeIP:nodePort` -> pod-network route. A VM parked in its own kube-ovn VPC is isolated from
`ovn-cluster` by design, so that hop has nowhere to go:

| VM | Subnet | VPC | Result |
|---|---|---|---|
| `win10-demo`                             | `ovn-default` `172.16.2.52` | `ovn-cluster`                    | RDP answers on `34.159.77.166` |
| `kdp-10p3s8dupeeavcyy-dev-ubuntu-kcp-vm` | `kdp-...-ubuntu-vm-subnet` `10.0.0.5` | `kdp-...-ubuntu-vm` | IP `34.141.127.80` assigned, TCP opens, **no SSH banner** |

This is the same isolation `../README.md` records for the bastion's earlier multus NAD. It
is a tenant-network constraint, not a KubeLB fault: every KDP VMaaS VM lands in a per-tenant
VPC, so publishing those needs a route out of the VPC (a kube-ovn VPC NAT/egress gateway, or
attaching the VM to `ovn-default` the way `bastion-vm.yaml` does).

## Why this matters for the bastion

`svc/acbd7ec2eff89440a9e1a044469217e2` in `kubermatic-virtualization` is the `kubevirt-ccm`
mirror of `bastion-vm` in `vm-aas-demo` on the routing cluster `khf59tv58t`, and it has
been `<pending>` for three days. The routing cluster's own LoadBalancer has no working
backend because this hop never resolves. A working CCM here is what closes that chain -
though as noted above, that mirror Service cannot be opted in without dropping
`useLoadBalancerClass`.

## Chart quirk: the CCM cannot write Events

The chart's leader-election Role grants no `events` verbs, so the pod logs this once at
startup and then never emits an Event again:

```
events is forbidden: User "system:serviceaccount:kubelb:kubelb-ccm"
  cannot create resource "events" in API group "" in the namespace "kubelb"
```

Harmless - leader election itself works and reconciliation is unaffected - but it means
`kubectl describe svc` will never show a KubeLB reason for a Service that fails to publish.
Use `just kubelb-logs` instead.

## The three KubeLB transport concepts, kept apart

Easy to conflate, and they solve different problems. From
`kubelb-ee/api/ee/kubelb.k8c.io/v1alpha1/config_types.go` (v1.5.0):

| Field / kind | Values | What it changes |
|---|---|---|
| `backendTransport.mode`     | `Direct` (default), `MTLS` | How the **management** Envoy reaches the tenant. `Direct` = node address + workload NodePort. `MTLS` = through a KubeLB-managed Envoy proxy inside the tenant cluster. EE only, Beta/Tech Preview. |
| `backendTransport.udp.mode` | `Tunnel` (default), `Direct` | UDP carriage **inside MTLS mode only** - `Tunnel` wraps each session in CONNECT-UDP over the mTLS port. Explicitly "has no effect in Direct mode". |
| `Tunnel` CRD (`tunnels.kubelb.k8c.io`) | n/a | A separate EE feature with its own `tunnel.connectionManagerURL`, for clusters with no inbound reachability at all. Not a `backendTransport` value. |

This tenant shows `mode: Direct` with `udp.mode: Tunnel` and a populated
`tunnel.connectionManagerURL`, which reads like three things are on. Only the first applies:
the UDP setting is inert in Direct mode, and the connection-manager URL is just the manager's
global tunnel config projected into every TenantState.

**None of them fix the VPC problem.** `MTLS` swaps a per-service NodePort for a tenant Envoy
proxy, but that proxy is a DaemonSet/Deployment on the tenant nodes, on the cluster pod
network - its hop to a VM at `10.0.0.6` in a custom kube-ovn VPC fails exactly as kube-proxy's
does today. MTLS changes the management-to-tenant hop; the break is the tenant-to-backend hop.
